# 持久检查点、计划版本与局部恢复

当前实现支持：步骤与尝试独立落库、不可变计划版本、依赖就绪调度、恢复时复用有效成功步骤。恢复重新执行未完成步骤，不是恢复 Python 调用栈，也不是逐 token 接续未完成的模型输出。默认仍只有一个公开工具 `web_search`。

## 数据与关联

新增四张表，启动时自动创建，不修改或删除旧表：

| 表 | 内容 |
| --- | --- |
| run_checkpoints | 用户/任务归属、执行代次 generation、当前计划版本、原输入及历史快照、配置指纹、恢复次数 |
| plan_revisions | 每个 run 的完整依赖图快照、版本、修订原因和失效步骤集合 |
| step_checkpoints | 当前步骤状态、结果、输入指纹和复用来源版本 |
| step_attempts | 每次尝试的参数、执行代次、状态、结果/错误、时间和是否允许安全重放 |

关系为 `用户 → 会话 → agent_run → 计划版本 → 步骤/尝试`。步骤键 `step:1` 等对应依赖图节点；`stage:intent`、`stage:review:1`、`stage:answer` 是聊天控制阶段检查点，内部使用 version=0，不是额外注册的工具。旧 task_checkpoints 预留表不参与新执行路径。

工具开始前提交 running 尝试记录，完成后立即提交结果。独立分支不需要等待整批结束才保存。每次 SQL 操作是短事务，外部工具调用不持有数据库事务。结果保存失败不会假装步骤成功；没有成功持久化的外部结果可能需要重新获取。

检查点只保存模型/检索配置的指纹，不保存 API Key。输入、历史、工具参数和输出属于当前用户的持久数据，应按聊天数据一起备份和保护。`include_results=true` 的检查点接口可以读取本人的步骤参数与输出，默认只返回元数据；尝试记录最多返回最近 100 条。

## 恢复流程

1. 启动时将遗留 running 尝试标为 unknown，未完成任务标为 interrupted，并增加执行代次，拒绝旧执行者回写。
2. 用户在消息的“检查点”面板查看状态，点击“从检查点继续”。也可调用恢复接口。
3. 后端校验用户归属、预期 generation、会话是否空闲、是否仍是该会话最新轮次、配置指纹及恢复预算。
4. 在同一事务中重新占用会话并增加 generation，进入原有公平队列，沿用原任务 ID 和原始历史快照。
5. 已持久化且仍有效的 succeeded 步骤直接复用；失败、跳过或未完成步骤重新参与依赖调度。模型路由、检索评估、最终回答也分别复用或重做。
6. 成功恢复后更新原助手消息，不额外插入一遍用户提问。其他用户不能查看或恢复此任务。

当前为**手动恢复**，重启不会自动批量重新执行任务。升级前已存在、没有新检查点的旧任务不能追溯恢复。若会话已经产生后续消息，拒绝回改旧轮次；请在新会话继续。模型/密钥/检索配置或工具检查点版本不兼容时，同样拒绝恢复，避免把旧上下文静默发往另一个服务。

## 依赖调度与计划修订

```text
版本 1：A、B、C 并行；A 失败，B/C 成功
版本 2：增加 B → A，并将 A 参数引用到 B 的输出
恢复：复用 B/C，只执行 A
```

每次修订提交完整 Plan、expected_version 和原因。服务端验证步骤数、ID、工具注册、依赖存在性、无环，以及参数引用确实存在依赖路径。它不自动猜测新依赖；调用方或用户明确提交修订，服务端校验后生效。

版本不可覆盖，只能递增。改变节点定义、参数、依赖，或删除节点时，会使该节点及旧/新依赖图上的传递下游失效；改变全局槽位保守地使所有旧节点失效。定义及上游未变的成功节点复制到新版本并标记复用来源。最终汇总缓存失效；聊天检索步骤被修订时相关评估也会重做。保存修订不自动执行，随后调用 resume。

执行器在每个节点完成后立即判断下游，不再等待同批所有独立节点。例如 B 完成且 A 只依赖 B，即使 C 尚未完成，A 也可进入空闲执行槽。失败只阻塞依赖后续；关键失败影响整体成功，独立分支仍继续。

这不是实时数据新鲜度判断。复用的是原任务的已确认结果；若要重新检索新数据，应修订相关节点。若 A 改变，使用 A 结果的 D 也会重做；不能只换 A 而沿用 D 的旧结果。

## API

所有接口要求登录并校验任务归属，跨用户返回 404：

| 方法 | 路径 | 内容 |
| --- | --- | --- |
| GET | `/runs/{id}/checkpoint` | 代次、计划版本、当前图、步骤状态、修订历史、最近尝试 |
| GET | `/runs/{id}/checkpoint?include_results=true` | 额外返回本人的参数和结果 |
| POST | `/runs/{id}/resume` | `{ "expected_generation": 2 }`，202 返回受理状态 |
| POST | `/runs/{id}/plan/revisions` | `{expected_version,reason,plan}`，保存新版本 |
| POST | `/runs/graph` | `{user_input,conversation_id?,model?,client_request_id?,plan}`，提交显式依赖图，202 返回 run_id |

普通 `/chat` 和 `/chat/stream` 自动接入检查点，不需要调用方构造图。显式依赖图入口只允许已注册工具，不开放内部模型阶段作为用户可指定工具。

显式图示例，B/C 可并行，A 使用 B 的 query：

```json
{
  "user_input": "检索并整理这些公开资料",
  "plan": {
    "intent_id": "web_search",
    "steps": [
      {"step_id": 1, "tool_name": "web_search", "depends_on": [2], "params_template": {"query": "{{steps.2.result.query}}"}},
      {"step_id": 2, "tool_name": "web_search", "depends_on": [], "params_template": {"query": "ReAct paper"}},
      {"step_id": 3, "tool_name": "web_search", "depends_on": [], "params_template": {"query": "agent planning"}}
    ]
  }
}
```

运行或排队期间不能改图；旧 expected_version、重复恢复和非最新轮次返回 409。更新 generation 后，旧执行者的步骤和最终结果写入都会被拒绝。

## 预算和结果未知

- 聊天检索保留全任务最多 3 次搜索尝试，失败及结果未知的尝试占预算，恢复和改图不重置。预算耗尽请新建请求，不通过恢复绕过上限。
- 显式 DAG 不使用聊天三轮循环，仍受每步骤累计尝试、最大步骤数、修订次数、恢复次数、总执行超时、用户配额和依赖熔断限制。
- 默认 `CHECKPOINT_MAX_STEPS=64`、`CHECKPOINT_MAX_VERSIONS=12`、`CHECKPOINT_MAX_RESUMES=5`、`CHECKPOINT_MAX_STEP_ATTEMPTS=6`、`CHECKPOINT_MAX_PARALLEL_STEPS=4`、单个检查点值最多 2000000 字节。配置模板已补充，修改需重启。
- `web_search` 标为 replay_safe，可在结果未知后重新读取。未来工具默认 replay_safe=false；若崩溃/取消发生在有副作用调用中，禁止自动重放。需要人工核对外部结果或使用外部幂等机制，不能承诺恰好一次。
- 工具实现语义改变时必须提高 `checkpoint_version`，避免旧检查点被错误复用。
- 中断的模型生成可能重新请求模型，已经发生的外部计费不会撤销。部分流式文本不等同于完整阶段检查点。

仍使用 SQLite 和单 API worker，本机进程锁仍保留。持久化恢复不等于分布式任务接管，也没有跨实例自动调度。升级先停旧服务并备份 data；新增表建好后，新任务才获得这些恢复能力。
